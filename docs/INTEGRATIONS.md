# Device and Fleet integration boundaries

The first-party collector executes Node OS/filesystem reads. On macOS it invokes only `/usr/bin/fdesetup status` and `/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate`, with a two-second timeout and 4 KiB output cap. It neither changes settings nor invokes a shell. Unknown or inaccessible values remain null. Linux/container collection does not infer disk encryption, host firewall enforcement, patch age or MDM from incomplete container visibility. Windows posture checks are accepted through the schema but no native Windows collector commands are implemented.

Optional network diagnostics use the operator's `PROBE_HOST` setting, resolve once, connect to the selected address, verify TLS with the original hostname and system trust, and report only pass/fail/unknown and duration. They do not authenticate to SaaS, capture packet content, query arbitrary API-supplied hosts or change networking. Automated tests exercise real loopback DNS/TCP and rejection of a non-TLS endpoint. This does not establish successful SaaS or VPN connectivity in a remote workforce.

The device API receives strict snapshots through a credential bound to tenant/device. Manual and Fleet imports require an operator role and are labeled by source. No recovered key, arbitrary environment field, raw command output or personal account field is accepted in a snapshot. Protect collector output when running it locally; public demo receipts omit actual workstation readings.

The optional Fleet adapter reads only `GET /api/v1/fleet/hosts/{configured-id}` at a fixed HTTPS origin, with a dedicated token. It validates matching numeric ID, supported platform, `seen_time`, and bounded policy responses. Configuration maps expected IDs for encryption, firewall, patch-age policy, administrator-count policy and MDM enrollment policy. Only faithfully representable boolean checks are projected. Numeric patch/admin values remain null and diagnostics remain unavailable rather than zero. Missing policy, unsupported response shape, mismatched host or oversized response fails or stays unknown as appropriate. No write, remote command, enrollment, wipe, escrow or recovery-password route is implemented.

[Official Fleet API](https://fleetdm.com/docs/api/rest-api) describes the broader product. These tests exercise the stated projection against native-shaped synthetic responses, not an actual Fleet instance. Live acceptance needs a dedicated read-only account, explicitly bound devices and policy semantics validated by the operator. Passing policy responses do not attest a physical device or establish compliance.
